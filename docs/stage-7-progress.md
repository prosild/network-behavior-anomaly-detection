# 단계 7 진행 기록: 모델 교체·재적재·롤백

기준: [최종 설계](../FINAL_PROJECT_DESIGN.md) 8절("새 작업 경계에서 묶음을 적재하고 실제 사용 버전·샘플 추론·스키마를 확인한다. 이전 묶음 복원 후 실제 추론 버전까지 확인해야 롤백 완료다"), [체크리스트](../IMPLEMENTATION_CHECKLIST.md) V6("alias 변경 화면만으로 롤백 시연을 완료하지 않는다").

## 첫째 작업: 결합 v2 묶음 등록, 교체·롤백 시연(2026-11-19, 배포 VM)

### 시작할 때 발견한 문제
- 결합 v2([DD-018](design-decisions/DD-018-fusion-merge-overlaps.md))와 검토 경로(DD-019) 배포 때 `zeek_ad/fusion.py`·`bundle.py`를 VM에 올렸다. 채점 worker는 묶음 manifest의 코드 해시와 지금 코드가 같아야 묶음을 쓴다([zeek_ad/worker.py](../zeek_ad/worker.py) `resolve_bundle`). 그래서 champion(버전 1)이 "묶음을 만든 뒤 코드가 바뀌었다"로 거부되는 상태였다. 이때 실습망 파일이 들어왔으면 채점이 실패했다.
- 그 사이 트래픽이 없어 실패한 작업은 0건이다(확인). 배포할 때 묶음 코드 파일을 바꾸면 묶음도 새 버전으로 등록해야 한다는 것을 놓쳤다.
- 등록 중 하나 더: VM의 `evaluation.py`가 이 PC와 달랐다(스무째 작업에서 docstring 세 줄만 고치고 VM에 올리지 않음). 등록 스크립트가 같은 검사로 막았고, 파일을 맞춘 뒤 등록했다.

### 규칙(설계 8절 그대로, 이번에 도구로 만듦)
- 코드가 바뀌면 묶음을 다시 만들고, CIC 다섯 캡처의 창 점수가 원래 평가와 같은지 재현 검사를 통과해야 새 버전으로 등록한다. 버전 1은 이전 코드용으로 남는다.
- 승격은 손으로 한다. 묶음을 만들 때 champion을 자동으로 붙이지 않는다.
- 채점 작업은 시작할 때 alias를 버전 번호로 고정한다. 작업 = 입력 + 묶음이라 한 작업 안에 두 버전 점수가 섞이지 않는다.

### 바꾼 것
- [scripts/build_bundle.py](../scripts/build_bundle.py): `--fusion`(결합 설정 선택, 묶음 폴더 `outputs/bundles/<설정 ID>/<시각>/`), `reproduction.json`, 자동 champion 지정 제거(`--alias`를 줄 때만).
- [scripts/register_bundle.py](../scripts/register_bundle.py)(새 파일): 묶음 폴더를 Registry 새 버전으로 등록(재현 통과·코드 해시 확인 뒤), `--set-alias ALIAS VERSION`(승격·롤백). 이 PC와 VM에서 같은 방법으로 쓴다(VM에는 재현에 쓰는 CIC 자료가 없다).
- [scripts/check_bundle.py](../scripts/check_bundle.py)(새 파일): alias가 가리키는 묶음으로 실제 추론을 하고 저장된 작업과 비교한다. DB에 쓰지 않는다. 같은 입력의 작업이 이미 있으면 worker는 건너뛰므로 롤백 확인에 쓴다.
- [scripts/live_agent.py](../scripts/live_agent.py) `revision_for_job`: 작업의 리비전 폴더를 `pipeline.json`의 작업 번호가 아니라 입력 지문(`scoring_job.input_manifest_sha256`)으로 찾는다. 묶음을 바꿔 같은 리비전을 다시 채점한 작업을 찾지 못하던 문제(작업 44). 시험 1개 추가, 전체 178개 통과.

### 시연(배포 VM, 실습망 `lab-20261119`의 최신 리비전 rev-0014)
1. champion 1 → 2. 같은 입력으로 새 작업 43(`zeekad-fusion/2`): 작업 42(`zeekad-fusion/1`)와 창 점수 567행·사건 52건(순위·ID·모델·점수·창)이 모두 같다. 코드를 바꿔도 v1 규칙의 결과는 그대로다.
2. 교체: champion 2 → 3. 새 작업 44(`zeekad-fusion/3`): 창 점수는 같고, 여러 모델이 겹쳐 꼽은 사건 둘만 합쳐졌다(1위 재생 자산 창 2 → 3, 6위 배포 VM 창 2 → 5). DD-018의 사후 계산과 같다.
3. 롤백: champion 3 → 2. `check_bundle.py`로 실제 추론: `zeekad-fusion/2`(overlap_policy skip)가 작업 43과 같고 작업 44와는 사건이 다르다.
4. 다시 champion 2 → 3, 실제 추론이 작업 44와 같다. **최종 champion은 버전 3(결합 v2)**. 이 PC 등록소도 같게 맞췄다.
5. 에이전트(작업 44): 범위가 바뀐 사건 2건만 다시 처리했다(늘어난 사건). LLM 보고서 2건 검증 통과, 판단 모델은 둘 다 analyst_review. 합친 배포 VM 사건(04:15\~04:40)의 보고서는 Kali 스캔(572개 포트, REJ 622건)과 B 클라이언트의 HTTP(각 147건)를 함께 설명한다. 합친 사건에 정상 배경 창이 붙는 DD-018 한계가 실제 보고서에 드러났다. 이미 알린 사건이라 Slack은 다시 보내지 않았다.

### 세그먼트 센서 확장(DD-020)
- 공격 대상을 배포 VM이 아닌 타깃 VM(lab-target 10.10.0.20)으로 두면 Kali↔타깃은 배포 VM이 당사자가 아닌 제3자 통신이다. 배포 VM을 세그먼트 전체를 promiscuous로 보는 센서로 쓰기로 했다(DD-015 결정 5에서 미뤄 둔 확장). 수집 명령은 그대로다(`tcpdump -i $LAB_IFACE`는 호스트 필터가 없고 기본으로 promiscuous).

### 해석(중요)

### 고친 것
- [zeek_ad/quota.py](../zeek_ad/quota.py)(새 파일): 한도 초과 차단기.
  - `Breaker`: 429를 한 번 보면 열린다. 실행(프로세스) 하나 동안만 산다.
  - `GuardedClient`: `genai.Client`를 감싼다. 429면 차단기를 열고, 열린 뒤의 호출은 네트워크 없이 `QuotaExhausted`를 던진다. `llm_report.py`·`send_decision.py`·`rag.py`는 평가 동결 파일이라 고치지 않고, 그 함수들에 넘기는 클라이언트를 감싸는 방식이다.
  - `retrieve_once`: 운영 검색. 질의 임베딩을 한 번만 시도하고 실패하면 바로 BM25.
- [zeek_ad/agent_graph.py](../zeek_ad/agent_graph.py): rag·write_report·decide가 차단기를 거친다. 임베딩과 LLM은 한도가 달라 차단기를 따로 둔다.
  - 임베딩이 막히면 BM25로 찾고 흐름은 이어진다.
  - LLM 보고서·판단 모델이 막히면 템플릿 보고서만 남기고(전송 판단 없음) 그 사건을 실패로 끝낸다. 판단이 없는 사건은 기존 규칙(`report_reason`의 'retry')대로 다음 실행이 다시 고른다. 정책 규칙의 템플릿 알림은 1차에서 이미 나간다.
  - 한도 초과 때의 템플릿은 그 (작업, 사건)에 보고서가 없을 때만 쓴다(`save_report(overwrite=False)`). 앞 시도의 LLM 보고서를 덮지 않는다.
- [scripts/run_agent_graph.py](../scripts/run_agent_graph.py): 판단 모델 클라이언트의 SDK 내부 재시도를 끈다(`retry_options.attempts=1`). 설정 전후 `max_retries` 4 → 0을 확인했다.
- [scripts/live_agent.py](../scripts/live_agent.py): `--redo-failed-calls`(호출 실패로 끝난 사건을 다시 고름, [agent_store.py](../zeek_ad/agent_store.py) `failed_call_incidents`), `--only <사건 ID>`.
- 효과: 한도 초과 상태에서 한 실행의 429는 임베딩 1번 + LLM 1번이다. 감시 프로그램이 `agent_retries`(2)번 다시 부르므로 파일 하나에 최대 6번 정도다(이전에는 사건 수 × 18번). 실행은 대기 없이 끝난다.
- 한계: 한도가 풀려도 새 파일이 오지 않으면(다시 계산이 없으면) 재시도 2번 뒤로는 다시 부르지 않는다. 그때는 `live_agent.py --capture <캡처>`를 손으로 부른다.
- 하지 않은 것: 늘어난 사건을 매번 다시 보고하는 규칙(DD-016 결정 3)은 그대로 둔다(Q70).

### 판정 기준(Q75, 사용자 결정)
- "공격 창에서 모델 후보였다"만으로는 판정할 수 없었다. 대상 VM(10.10.0.20, originator)은 11-22에 공격 없는 창 54개 가운데 49개에서도 꼬리 희귀도 후보였다.
- 잡힘 = 공격 창에서 나온 알림 + 평소(같은 자산·역할의 공격 없는 창)보다 높은 모델. 구분 안 됨 = 알림은 있으나 평소보다 높은 모델 없음. 후보만 = 후보였으나 공격 창에서 나온 알림 없음. 놓침 = 후보 아님.
- 알림은 그 알림을 기록한 작업에서 사건이 가졌던 창이 공격 창과 겹칠 때만 센다. 걸린 시간은 첫 공격 연결부터 첫 알림 기록(dry-run 기록 시각)까지다.

- 새로 드러난 것: 공격 전부터 이어지던 사건에 공격 창이 붙으면 새 알림이 나가지 않는다(DD-016의 "이미 알린 사건은 다시 알리지 않는다"). 대상 VM처럼 늘 사건으로 잡히는 자산에서 시작한 공격(비커닝, 유출)은 이 때문에 알림 없이 지나갔다. 표에 "흡수됨"으로 적었다. 브로드캐스트 오탐을 줄이면 이 자산의 상시 사건이 사라지므로, 그 뒤에 다시 재 볼 값이다.

### 검증
- 설계 세션이 다시 실행: `check_lab_truth.py` 통과(11개 일치, 겹친 연결 0), `build_lab_detection.py` 종료 코드 0, 전체 시험 253개 통과(기존 196 + 새 57).

  - 구분 안 됨의 알림 시각(비커닝 1회차 20.9분)은 탐지 시간으로 쓰지 않는다.

### 한계
- 종류마다 1\~2회 실행이라 비율이 아니다. Kali와 대상 VM의 받는 쪽은 견줄 평소 창이 1\~2개뿐이다(연결 확인). 실습망 정상 트래픽으로 기준선을 넓혀야 풀린다(Q73의 5번 항목).

## 열일곱째 작업: 브로드캐스트 오탐 줄이기(2026-11-26, DD-021·Q76·Q77)

### 배경
- 외부 피드백의 사건 #2271(`10.10.0.20 → 10.10.0.255:138/udp` 한 건이 High 경보). 대상 VM의 Samba가 5분쯤마다 보내는 NetBIOS 브로드캐스트다. 브로드캐스트 주소는 자산이 아니지만 그리로 보낸 연결은 보낸 쪽의 창 특징에 남는다.
- 억제 전(캡처의 마지막 작업 기준): 유휴 3일의 사건 118·118·35건이 전부, 공격한 날은 88건 중 67건이 이런 창뿐인 사건이었다. LLM 보고서도 유휴 3일은 전부(52·118·35건) 여기서 나왔다. 배포 VM을 켜 두면 공격이 없어도 Gemini 호출이 이어져 `pipeline`·`collector`를 멈춰 두었다(열다섯째 작업).

### 결정([DD-021](design-decisions/DD-021-queue-eligibility-non-host-only.md))
- 자산이 그 창에 건 연결이 전부 호스트가 아닌 주소(내부 대역의 네트워크·브로드캐스트 주소, `255.255.255.255`, 멀티캐스트)로 갔고 그 수가 25개 이하인 originator 창은 점수를 남기되 조사 큐에 올리지 않는다(`split = non_host_only`).
- 세 방식 가운데 사용자가 "큐에서 빼기"를 골랐다(Q76). 특징에서 빼면 학습과 운영의 특징 정의가 달라지고, 분석가 예외 규칙은 계약·DB·양쪽 구현이 든다.
- 상한은 사용자의 질문("왜 브로드캐스트만 쓰는 활동은 알림이 안 나가게 정하나", Q77)에서 나왔다. 수와 무관하게 빼면 브로드캐스트 폭주도 가려진다. 25는 CIC 월요일 정상 창에서 본 최대다(originator 창 1,227개, 창당 호스트가 아닌 주소행 연결 수 중앙 1·p99 12·최대 25).
- 모델이 이 창을 가리지 못하는 이유도 같은 측정에서 나왔다. 월요일에는 그런 연결만 있는 창이 0개다. 학습 자료의 호스트는 쉬지 않아서, 조용한 호스트의 창 자체를 본 적이 없다.

### 구현(작업자)
- 규칙은 채점 worker에서 점수를 낸 뒤 큐를 만들기 전에 적용한다. 묶음 코드 아홉 파일(`scripts/build_bundle.py`의 `CODE_FILES`)은 한 글자라도 바꾸면 worker가 등록된 묶음을 거부하므로(첫째 작업), 묶음 밖에 두었다. 묶음 재등록과 재학습이 없다.
- [zeek_ad/queue_eligibility.py](../zeek_ad/queue_eligibility.py)(새 파일): 주소 판정, 창 판정, 창 점수 표에 라벨 붙이기, 입력 지문에 넣을 기록. [configs/worker/queue-eligibility.v1.json](../configs/worker/queue-eligibility.v1.json): 라벨, 대상 역할, 상한과 그 출처.
- [scripts/run_worker.py](../scripts/run_worker.py): 점수 → 규칙 → 라벨 창을 뺀 표로 큐 → 라벨을 바꾼 전체 표를 DB에 쓴다. 출력 줄에 뺀 창 수와 상한을 넘어 남긴 창 수를 적는다.
- [scripts/live_recompute.py](../scripts/live_recompute.py): 리비전의 `worker-inputs.json`에 `queue_eligibility` 항목을 넣는다. 규칙 설정과 자산 설정은 리비전 폴더(`queue_eligibility/`)에 복사해 그 사본을 쓴다. [configs/pipeline/live.v1.json](../configs/pipeline/live.v1.json)에 켜고 끄는 키(기본 켬).
- 작업 식별: 규칙이 적용된 작업은 입력 지문에 규칙 설정·자산 설정·Silver manifest의 해시가 들어간다([zeek_ad/worker.py](../zeek_ad/worker.py) `set_input_fingerprint`, worker와 `live_agent.revision_for_job`이 함께 쓴다). 항목이 없는 입력(CIC·합성, 옛 리비전)의 지문은 예전과 같다.
- 연결 자료는 리비전의 Silver다(Gold 창 배정의 직접 원천). 실행할 때 Gold의 originator 창이 모두 연결 자료에 있는지 대조하고, 어긋나면 작업을 실패로 끝낸다.
- [scripts/measure_queue_eligibility.py](../scripts/measure_queue_eligibility.py): 억제 전후 측정과 상한 출처 재현. [scripts/check_bundle.py](../scripts/check_bundle.py)도 같은 규칙을 적용해 비교한다.
- [zeek_ad/lab_detection.py](../zeek_ad/lab_detection.py): 평소 창을 "큐에 오를 수 있는 공격 없는 창"으로 적고, 이 라벨이라 평소 창에서 빠진 수를 결과에 남긴다(동작은 그대로, 지금 결과의 판정·숫자도 그대로).

  - 반영한 지적: 지문이 리비전 밖의 공용 설정 파일에 묶여 있던 것(설정을 고치면 이미 만든 리비전을 찾지 못함 → 리비전에 사본을 둠), worker 연결 부분의 시험 공백(결함 다섯 가지를 넣어도 통과 → 함수로 빼서 가짜 모델로 시험), 내부 대역이 겹칠 때 자산 규칙과의 불일치, 탐지 표의 평소 창 뜻.
  - 보완 뒤의 코드는 독립 검토를 다시 받지 않았다. 설계 세션이 변경 내용을 읽고 위 명령으로 확인했다.
- 확인하지 못한 것: DB와 MLflow가 있는 환경에서 worker를 끝까지 돌리는 것(이 PC에는 떠 있지 않다). 배포 VM에서 확인한다.

### 배포 VM 반영과 확인(같은 날, 커밋 `8082793`)
- 반영: 코드·설정·시험 파일을 `rsync`(체크섬 비교)로 올려 VM과 로컬의 차이를 0으로 맞췄다. 묶음 코드 파일의 해시는 로컬과 VM이 같다. `pipeline` 이미지를 다시 만들었다.
- 켜기 전 확인(DB에 쓰지 않고 실제 묶음으로 추론)
  - 새 이미지 안에서 관련 시험 116개 통과.
  - `check_bundle.py`로 옛 리비전(`lab-20261125` rev-0036, 규칙 항목 없음)을 다시 추론: champion(버전 3)이 거부되지 않고, 저장된 작업 355와 창 점수 108행·사건 35건이 같다. 옛 경로는 그대로다.
  - 같은 입력에 규칙 항목을 넣어 다시 추론: 사건 35건 → 0건. 컨테이너 안에서 Silver를 읽는 새 경로가 돈다.
