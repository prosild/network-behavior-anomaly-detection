# DD-020. 배포 VM을 실습망 세그먼트 전체를 보는 센서로 쓰고, 공격 대상 VM을 추가한다

- 결정일: 2026-11-22
- 요청·결정: 사용자(공격 종류를 늘려야 네트워크 이상탐지 프로젝트라 할 수 있다, 타깃 VM을 추가하자). 수집 구조·검증 방법은 Claude가 정했다.
- 관련: [DD-015](DD-015-vmware-lab-deployment.md)(결정 5에서 "피해 VM 추가와 실습망 엿보기는 이후 확장"으로 미뤄 둠), [DD-016](DD-016-lab-capture-coverage-and-report-refresh.md), [DD-017](DD-017-lab-background-traffic.md), [설계 질문 기록](../design-discussion-log.md) Q69

## 배경
- 지금까지 실습망 시험은 nmap 스캔 하나뿐이었다(DD-017 시간표). 공격 대상이 모두 배포 VM 자신이라, 수집 카드가 트래픽의 당사자였고 다 보였다.
- nmap 스캔은 5분 안에 거부 연결이 수백~수천 건 생기는 시끄러운 공격이라, 창 하나만 보는 통계 모델(꼬리 희귀도)로도 잡힌다. Transformer·TGN을 넣은 이유인 문맥적·관계적 이상(비커닝, 느린 유출, 측면 이동)은 실습망에서 한 번도 돌리지 않았다. 네트워크 이상탐지 프로젝트로서 가장 큰 공백이다.
- 공격 대상을 배포 VM이 아닌 다른 내부 호스트로 두면 Kali↔타깃은 **배포 VM이 당사자가 아닌 제3자 통신**이다. 스위치가 당사자에게만 프레임을 보내면 배포 VM의 수집 카드에 오지 않는다. 그래서 타깃 VM 추가는 수집 구조 변경을 동반한다.

## 결정
1. **배포 VM을 세그먼트 센서로 쓴다.** 실습망(VMnet2, 10.10.0.0/24)의 모든 트래픽을 배포 VM의 실습용 카드가 promiscuous로 캡처한다. 실제 IDS가 미러 포트에서 세그먼트를 관찰하는 구조와 같다.
   - 수집 명령은 바꾸지 않는다. `scripts/capture_rotate.sh`의 `tcpdump -i $LAB_IFACE`는 호스트 필터가 없고, tcpdump는 기본으로 카드를 promiscuous로 올린다. 즉 코드 변경이 아니라 가상 스위치가 제3자 유니캐스트를 promiscuous 카드로도 뿌리는가의 문제다.
   - VMware Workstation의 host-only vmnet은 허브처럼 동작해 뿌린다. 2026-11-22 실측으로 확인했다(아래 "검증").
2. **공격 대상 VM(lab-target)을 추가한다.** Ubuntu Server 24.04, vCPU 2 / RAM 2GB / 디스크 20GB. 카드 둘: NAT(관리·패키지 설치용), VMnet2 고정 `10.10.0.20/24`(기본 경로 없음, IPv6 끔). 서비스는 SSH(22)·HTTP·Samba(445)를 올려 정찰·무차별 대입·비커닝·측면 이동의 대상이 되게 한다.
   - 타깃·Kali는 둘 다 `10.10.0.0/24` 안이라 [configs/assets.lab.v1.json](../../configs/assets.lab.v1.json)을 고치지 않아도 자동으로 채점 대상이 된다.
3. **측면 이동은 타깃을 복제해 2대 이상일 때 붙인다.** 한 대로 센서를 검증한 뒤 복제하면 둘째 타깃은 거의 공짜다. 지금은 한 대로 시작한다.
4. **시나리오 우선순위**: 비커닝 → 느린 스캔 → 느린 유출. 통계 모델이 못 보고 Transformer·TGN이 봐야 하는 문맥적·관계적 이상부터 채운다. Kali는 격리 실습망에만 있어 Claude가 직접 돌리지 않고, 생성 스크립트와 해석을 Claude가 맡고 실행은 사용자가 한다(DD-015·DD-017과 같은 역할 분담).

## 검증(2026-11-22)
- 게이트: lab-target에서 `python3 -m http.server 8080`, 배포 VM에서 `tcpdump -i ens34 -n host 10.10.0.20`, Kali(10.10.0.50)에서 ping·curl.
- 결과: 배포 VM의 tcpdump에 `10.10.0.50 ↔ 10.10.0.20`의 ARP·ICMP·TCP 3-way·HTTP가 양방향으로 다 떴다(당사자가 아닌데도 관찰).
- 파이프라인까지: 캡처 파일 `lab-20261122T134000Z`(18패킷)의 Zeek conn 로그에 ICMP(10.10.0.50→10.10.0.20)와 HTTP(10.10.0.50:44662→10.10.0.20:8080, service http, conn_state SF)가 들어갔고, 둘 다 `local_orig=true, local_resp=true`(양쪽을 내부 자산으로 인식). 채점 작업 45가 성공하고 10.10.0.20이 새 자산으로 채점됐다.

## 알아야 할 한계
- 타깃은 학습 이력이 없는 **새 자산(새 노드)**이라, 공격이 아닌 양성 트래픽에도 꼽힌다(검증에서 양성 ping만으로 후보 창 1개). DD-017의 재생 자산과 같은 성질이다. 탐지력 개선은 이후 과제이고, 지금은 해석에서 거른다. 타깃에 정상 배경을 미리 깔면 덜 튄다.
- 조용한 실습망에서는 공격 창이 담긴 마지막 파일이 다음 파일이 와야 채점된다(DD-016). Kali→타깃 게이트 파일도 채점 전 `zeek_done`에 머물렀다. 시나리오를 이어 돌리면 자연히 채점된다.
- promiscuous 캡처는 세그먼트의 모든 트래픽을 받는다. 자기 트래픽(DB·Gemini)은 처음부터 관리용 카드·localhost로 가므로 실습용 카드 캡처에 섞이지 않는다(DD-015와 같다).
- 타깃의 NAT 카드는 패키지 설치·관리용이다. 공격 시험 중에는 연결을 끊어(또는 유지해도 라우팅하지 않으므로) 실습망 격리를 지킨다.
