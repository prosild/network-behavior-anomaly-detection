# DD-004. 단일 호스트 Spark Standalone 클러스터 실행 추가

- 결정일: 2026-11-04
- 요청·결정: 사용자. 실행 방식(B안)은 Claude가 제안했다.
- 목적: Spark는 채용 우대사항이다. 코드 작성뿐 아니라 클러스터 배포·제출·운영을 작게라도 직접 겪는다.
- 관련: [설계 질문 기록](../design-discussion-log.md) Q16, [단계 2 진행 기록](../stage-2-progress.md)

## 바뀌는 설계 내용

| 최종 설계 위치 | 이전 | 변경 |
| --- | --- | --- |
| 7절 "초기 실행은 단일 머신 `local[*]`" | local 모드만 사용 | local에서 개발·검증한 뒤, 같은 코드를 이 PC 위 Docker Compose Standalone 클러스터(master 1, worker 2)에 `spark-submit`으로 제출한다 |
| 10절 단계 2 완료 기준 | 재실행 동일성, 실행 계획 설명 | 추가: local과 클러스터 결과의 동일성, executor 장애 재시도 관찰 |

## 진행 순서

1. local `local[*]`에서 Silver·Gold를 완성하고 검증한다. 로직 오류와 배포 오류를 섞지 않기 위해서다.
2. 클러스터를 띄운다. master, worker, 제출용 컨테이너 모두 같은 이미지를 쓴다. 이미지에는 `zeek-ad`와 같은 Python·Java·PySpark 버전을 넣는다. driver와 executor의 버전이 다르면 실행이 실패하기 때문이다.
3. 같은 코드를 클러스터에 제출하고 결과를 local 결과와 비교한다.
4. Spark UI에서 executor별 작업과 shuffle 양을 확인한다. executor 하나를 일부러 종료하고 재시도를 관찰한다.

## 구현 원칙

- **master 지정 위치:** 코드에 `master`를 고정하지 않는다. 실행 명령이 정한다. 지정하지 않으면 PySpark 기본값인 `local[*]`로 돈다.
- **우리 코드 배포:** `zeek_ad`는 `--py-files`로 executor에 보낸다. `sys.path` 추가는 driver에만 적용되기 때문이다.
- **데이터 경로:** 모든 컨테이너에 프로젝트를 같은 경로로 마운트한다. 실무의 공유 저장소(HDFS, S3)를 대신한다.
- **자원 설정:** executor 메모리·코어는 설정 파일에 고정하고 실행 기록에 남긴다.
- **결과 비교:** 행 순서는 실행마다 다를 수 있다. 정렬한 내용이나 순서와 무관한 해시로 비교한다.

## 바꾸지 않는 것

- 다중 노드 처리 성능을 주장하지 않는다. 데이터가 약 1GB라 속도 이득이 없다. 소요 시간은 측정값 그대로 보고한다.
  - 포트폴리오 표현: "단일 호스트 위 다중 executor 클러스터에서 배포·제출·장애 재시도를 경험".
- Spark MLlib과 분산 학습은 필수로 만들지 않는다. 모델 학습은 Python worker가 맡는다(6절).
- Kubernetes와 클라우드 클러스터는 계속 범위 밖이다.
- 단계 6 스트리밍을 클러스터에서 돌릴지는 단계 6에서 정한다.
