# DD-012. 새 PCAP 파일 도착으로 시작하는 자동 파이프라인(파일 단위 마이크로배치)

- 결정일: 2026-11-17
- 요청·결정: 사용자. 방식 비교와 구성은 Claude가 제안했다.
- 관련: [설계 질문 기록](../design-discussion-log.md) Q42·Q43, [DD-005](DD-005-deadline-scope.md), 설계 7.3절·10절 단계 6

## 배경
- 사용자의 목표: 들어오는 네트워크 트래픽을 저장하고, 새 파일이 생기면 자동으로 읽어 전처리 → 모델 → 대시보드까지 이어지는 파이프라인.
- 지금 상태: 단계(Zeek, Silver, Gold, 그래프, 채점 worker, 근거, DB 뷰)는 모두 있다. 하지만 하루 캡처 전체를 단위로 사람이 명령을 실행한다. DD-005가 단계 6 스트리밍을 후속으로 미뤘기 때문이다.
- 사용자는 프로젝트가 끝난 뒤 Kali Linux 실습망에서 실제 트래픽으로 시험한다. CIC PCAP을 잘라 도착을 흉내 내지 않는다.

## 결정
1. **파일 단위 자동 처리**를 만든다. 정식 스트리밍(Structured Streaming·watermark·checkpoint)은 계속 후속이다.
   - 수집 장비가 일정 시간마다 자른 PCAP(예: `tcpdump -G 300`)을 수신 폴더로 **원자적으로 옮긴다**. 작성 중인 파일은 넣지 않는다(설계 7.3절의 "완성된 불변 파일" 원칙).
   - 감시 프로그램이 수신 폴더를 주기적으로 보고, 새 파일마다 Zeek를 실행한다. 이어서 그날(UTC 날짜)의 캡처 `lab-YYYYMMDD`를 **지금까지 받은 파일 전체로 다시 계산**한다: Silver → Gold → 그래프 → 채점 worker → 근거 → (선택) LLM 보고서 → DB.
   - 처리 기록은 DB 표에 남긴다. 같은 내용(해시)의 파일은 한 번만 처리한다.
2. **감시 프로그램은 기본으로 꺼 둔다**(`configs/pipeline/live.v1.json`의 `enabled: false`). 사용자가 Kali 시험 때 켠다. 켜는 방법은 [docs/live-pipeline.md](../live-pipeline.md)에 둔다.
3. DD-005의 "단계 6 후속"은 정식 스트리밍에 대해서만 유지한다. 파일 단위 자동 처리는 이 결정으로 범위에 넣는다. 마감 제약은 사용자 지시에 따라 고려하지 않는다.

## 정식 스트리밍과의 차이(문서화할 한계)
- 파일 경계에 걸친 연결은 파일마다 따로 기록되어 둘로 잘린다(Zeek를 파일마다 오프라인 실행하므로).
- 지연은 파일 회전 주기 + 처리 시간이다. 창 상태를 들고 있지 않고 그날 전체를 재계산하므로 비용은 하루 누적량에 비례한다.
- 재시작은 처리 기록으로 안 한 파일만 다시 한다. 재계산이라 같은 입력이면 결과가 같다.

## 실습망 시험 전에 필요한 것
- 실습망 내부 대역을 담은 자산 설정 파일(어떤 IP를 채점할지 정한다).
- 재학습은 요구하지 않는다(Q44, 2026-11-17). 목적은 모델 성능이 아니라 실제 트래픽을 받는 파이프라인이다. 실습망 점수는 "CIC 월요일 정상 트래픽과의 차이"라는 한계를 문서에 적는다.
