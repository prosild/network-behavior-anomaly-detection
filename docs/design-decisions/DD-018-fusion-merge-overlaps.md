# DD-018. 결합 v2: 여러 모델이 겹쳐 꼽은 사건은 하나로 합치고, 범위는 모든 모델 창의 합으로 한다

- 결정일: 2026-11-19
- 요청·결정: 사용자(Claude 추천대로). 문제는 실습망 실행 1·2에서 Claude가 찾았다.
- 관련: [DD-009](DD-009-rank-interleave-fusion.md)(결합 v1, 대체하지 않고 v2를 더한다), [DD-016](DD-016-lab-capture-coverage-and-report-refresh.md)(늘어난 사건·다시 알림), [DD-017](DD-017-lab-background-traffic.md), [설계 질문 기록](../design-discussion-log.md) Q59, [단계 6 진행 기록](../stage-6-progress.md) 스물둘째·스물셋째 작업

## 배경
- v1([fusion.v1.json](../../configs/models/fusion.v1.json), 2026-11-11 동결)은 모델마다 자기 후보 창으로 사건을 만들고, TGN → 꼬리 희귀도 → Transformer 순서로 1위, 2위를 번갈아 뽑는다. 같은 자산·역할에서 창이 겹치면 먼저 뽑힌 사건만 남기고 창은 늘리지 않는다.
- 실습망 실행 1(Kali `nmap -sT` 03:45, `nmap -sV` 03:50):
  - 작업 35에서 Kali 사건이 TGN 사건(03:50 한 창)으로 뽑혀 `-sT` 창이 빠졌다. TGN 점수가 같은 두 사건(11.74) 중 어느 쪽이 줄지는 입력 파일 해시로 정하는 동점 순서가 갈랐다.
  - 사건 ID(`캡처|자산|역할|첫 창`)가 작업 34의 03:45 사건과 달라져 같은 공격자가 Slack에 다시 알려졌다(DD-016의 "이미 알린 사건"은 ID 기준).
  - 실행 2에서 사건이 늘어 큐 순서가 바뀌자 같은 사건이 다시 03:45\~03:55로 바뀌었다. 사건 범위가 큐 구성에 따라 흔들린다.
- 입력은 세 모델이 같다. 판정(임계값을 넘는 창)이 다른 것은 의도이고, 문제는 결합 단계가 그중 한 모델의 창만 남기는 것이다(Q59).

## 결정
1. 새 설정 [fusion.v2.json](../../configs/models/fusion.v2.json)(`overlap_policy: merge_windows`). 모델·도는 순서·후보 규칙은 v1과 같다.
2. 겹친 사건은 건너뛰지 않고 먼저 뽑힌 사건에 합친다. 새 사건이 이미 뽑힌 사건 여럿과 겹치면(다리 역할) 그 사건들도 하나로 합치고, 순위는 그중 가장 먼저 뽑힌 자리다.
3. 합친 사건의 창 = 묶인 모든 모델 사건 창의 합. 모델 사건은 이어진 창이라 합친 범위도 이어진 창이다. 사건 ID·첫 창·끝은 합친 창으로 다시 만든다. 어느 모델이 먼저 뽑혔든 같은 활동이면 같은 ID다.
4. 모델별 30분 상한은 모델 사건에만 적용한다. 합친 사건은 넘을 수 있다.
5. `incident.model_score`는 처음 뽑은 모델의 사건 중 합친 범위 안에 든 것의 점수 최댓값이다. `also_flagged_by`에는 처음 뽑은 모델을 넣지 않는다.
6. 구현: [zeek_ad/fusion.py](../../zeek_ad/fusion.py) `fuse`(설정의 `overlap_policy`로 고름), `fuse_merge_overlaps`, `picked_score`. v1 함수(`fuse_round_robin`)는 그대로 둔다.
   - 이유: 등록된 묶음은 결합 설정만 묶음에서 읽고 결합 코드는 컨테이너 것을 쓴다(2026-11-19 VM에서 확인: 불러온 뒤 `zeek_ad.fusion`이 `/app/zeek_ad/fusion.py`). 코드 기본 동작을 바꾸면 등록된 v1이 몰래 바뀐다. `overlap_policy`가 없는 설정(v1)은 예전과 같다.
7. CIC 결합 평가 결과(v1, DD-009)는 바꾸지 않는다. v2는 동결 뒤 실습망 결과를 보고 정한 것이라, CIC에 다시 적용한 숫자를 내면 "사후 비교"로 표시한다.

## 알아야 할 한계
- 합친 사건은 길어질 수 있다. 공격 앞뒤로 한 모델이 꼽은 정상 창(예: 배포 VM이 B의 HTTP 서버가 된 배경 칸)이 공격 사건에 붙는다. 근거·보고서는 합친 범위를 설명한다.
- 사건 ID는 여전히 첫 창에 묶여 있다. 뒤 파일에서 앞 창이 새로 후보가 되면(예: `capture_edge`였던 창이 `live`가 됨) 첫 창이 바뀌어 ID가 달라진다.
- 다리 역할 합치기로 이미 뽑힌 사건이 사라지면 그 뒤 사건의 순위가 하나씩 당겨진다.
