## 3. 인용할 표와 문장

전체는 [실습망 공격 탐지 결과](lab-attack-detection.md)에 있다.

| 공격 | 실행 | 판정 | 첫 알림까지 |
| --- | --- | --- | --- |
| 빠른 스캔 | 2회 | 잡힘, 잡힘 | 7.0분, 15.2분 |
| 서비스 스캔 | 2회 | 잡힘, 잡힘 | 6.8분, 10.2분 |
| 느린 스캔 | 1회 | 잡힘 | 6.9분 |
| 공유 탐색 | 1회 | 잡힘 | 3.6분 |
| 비커닝 | 3회 | 구분 안 됨, 후보만, 규칙 뒤 구분 안 됨 | 없음 |
| 분할 유출 | 2회 | 후보만, 규칙 뒤 잡힘 | 규칙 뒤 7.5분 |
| DNS 터널 | 1회 | 후보만 | 없음 |
| SSH 무차별 대입 | 1회 | 놓침 | 없음 |

인용할 때 지킬 것.

- 탐지율이 아니다. 종류마다 1\~3회 실행한 프로브다. "규칙 전의 기록에서 8종 중 4종을 잡았고, 오탐 규칙을 배포한 뒤 다시 돌린 분할 유출도 잡혔다"까지는 쓸 수 있고 퍼센트로 쓰지 않는다. 분할 유출의 "잡힘"은 점수 차가 작고 실행이 한 번이다.
- 판정의 뜻: 잡힘 = 공격 창에서 나온 알림이 있고 그 자산의 평소 창보다 점수가 높은 모델이 있다. 구분 안 됨 = 알림은 있었지만 평소보다 높은 모델이 없다. 후보만 = 모델 후보였지만 공격 창에서 나온 알림이 없다. 놓침 = 후보가 아니다.
- 걸린 시간은 첫 공격 연결부터 첫 알림 기록까지다. Slack은 dry-run이라 전송 시각이 아니라 기록 시각이다. 대부분은 5분 창이 닫히기를 기다리는 시간이고, 창이 닫힌 뒤로는 약 2분이다. 2회차 스캔(15.2분, 10.2분)은 배경 트래픽으로 사건이 몰려 채점이 밀린 경우다.
- 2회차 빠른 스캔과 서비스 스캔은 알림 하나에 함께 묶였다.

zeek_AD README에서 바뀐 표현(대시보드 README가 인용하고 있으면 맞춘다).

| 항목 | 전 | 후 |
| --- | --- | --- |
| 공격 종류 수 | 7종 | 8종(11회). 서비스 스캔을 따로 센다 |
| 분할 유출 | 약하게 | 후보만 |
| 비커닝 | 놓침 | 구분 안 됨(1회차), 후보만(2회차) |
| DNS 터널 | 놓침 | 후보만(서버 쪽 한 창만 후보, 알림 없음) |
| 스캔·공유 탐색 | 잡음 | 잡힘 + 첫 알림까지 걸린 시간 |
| 실습망 시험 이름 | 측면 이동 | 공유 탐색(풀어 쓸 때 "SMB 공유 탐색"). 한 일이 `IPC$` 연결과 공유 목록 조회라 ATT&CK의 Discovery(T1135)다. 내부 "4대"가 아니라 주소 4개다(타깃 VM 한 대와 별칭 주소 3개) |

CIC 평가 표(결합 v1 Recall@50 14/16, 합성 13/20 등)는 바뀌지 않았다.

이름은 사용자 결정으로 2026-11-26에 바꿨다. 식별자(`lateral_movement`, `slow_exfil`, `synthetic_apt_v1`, 스크립트 이름, 캡처 ID)는 그대로다. 찾으려는 행동의 예로 드는 "측면 이동, beacon, 느린 유출"과 합성 패턴 5종의 종류 이름은 실습망 시험 이름이 아니라서 바꾸지 않았다.

## 6. 종결한 사건 다시 열기(T53)

계약은 [데이터 계약 v2](data-contract-v2.md) "쓰기: 종결한 사건 다시 열기"에 있다. 결정과 이유는 [DD-022](design-decisions/DD-022-incident-reopen.md).

```sql
SELECT dashboard.reopen_incident(
    p_job      => 83,
    p_incident => 'lab-20261122|10.10.0.50|originator|1795362000',
    p_actor    => 'analyst01',
    p_reason   => '같은 출발지의 스캔이 다시 관측됨',
    p_expected_resolution => 'false_positive'   -- 선택(권장). 화면이 보고 있던 결론
);  -- 반환: 'investigating'
```

- **`dashboard.transition_incident`는 바뀌지 않았다.** `closed → investigating`은 지금처럼 `22023`으로 거부된다. 재개는 새 함수로만 한다.
- 함수를 나눈 이유: `transition_incident(p_to => 'investigating')`는 "분석 시작"에도 쓰인다. 같은 함수가 재개까지 받으면, 다른 사람이 종결한 사건을 오래된 화면의 "분석 시작"이 다시 열어 결론을 지운다(대시보드의 `IncidentTransitionService.transition`은 현재 상태를 보내지 않고 목표만 보낸다).
- 종결 상태일 때만 성공한다. 상태 `investigating`, 결론 null이 되고 이력에 `closed → investigating` 행이 남는다. 계정은 `dashboard_rw`다.
- `p_expected_resolution`을 보내길 권한다. 그 사이 다른 사람이 다시 열어 새 결론으로 종결했으면 `22023`("종료 결론이 화면과 다르다. 지금 결론: …")으로 거부된다.
- 거부: 종결이 아니면 `22023`("종료한 사건만 다시 열 수 있다. 지금 상태: …"), 사유·행위자가 비면 `22023`, 사건이 없으면 `02000`.
- 분석가 검토와의 관계: 검토에서 `dismiss`를 결정한 뒤 그 사건을 종결했다가 다시 열면, 파이프라인은 앞선 결정으로 다시 닫지 않는다. 이때 검토 뷰는 `dismiss`·재개됨인데 상태는 `investigating`이다. 재개 실패가 아니다.
- 배포 VM의 DB에는 적용했고 검증했다(`scripts/verify_incident_reopen.py`, 42개 확인 통과, `dashboard_rw`로 호출).
- 스냅샷 복원 DB: `db/migrations/018_incident_reopen.sql` 하나를 실행한다. 함수 하나와 그 소유자·권한만 정하고, 다시 실행해도 결과가 같다. 선행 조건은 migration 012까지 적용된 DB와 `zeekad_owner`·`dashboard_rw` 역할이다.
- 반영 순서: zeek_AD 파이프라인 이미지(끝) → migration 018(끝) → 대시보드의 "다시 열기" 버튼.

## 7. 브로드캐스트 오탐 규칙(피드백의 #2271)

- 자산이 그 5분 창에 건 연결이 전부 브로드캐스트·멀티캐스트 주소로 갔고 그 수가 25개 이하이면, 점수는 남기되 조사 큐에 올리지 않는다([DD-021](design-decisions/DD-021-queue-eligibility-non-host-only.md)). 실습망(live) 입력에만 적용한다.
- 대시보드 뷰에는 변화가 없다. 그런 사건이 새로 생기지 않을 뿐이다(이유는 `zeekad.window_score.split = 'non_host_only'`에 남지만 대시보드 뷰에는 나오지 않는다).
- 규칙은 배포 뒤의 새 캡처부터 적용된다. `lab-20261122`\~`lab-20261125`의 사건은 그대로 남아 있다. #2271 같은 옛 사건은 "규칙 전의 오탐 사례"로 보여 줄 수 있다.
- 억제 전후(저장된 점수로 큐를 다시 만들어 잰 값): 유휴 3일의 사건 271 → 0건, 공격한 날(`lab-20261122`) 88 → 21건. 공격 사건은 사라지지 않았다.
- 배포 뒤 실측(`lab-20261126`): 유휴 30분 동안 사건 0건. 같은 날 다시 돌린 비커닝과 분할 유출은 따로 사건이 되어 알림이 나갔다.
- `lab-20261126`의 LLM 보고서는 처음에 모두 연결 오류로 실패해 템플릿으로 남았다(배포 VM의 Docker 네트워크 문제, 코드와 무관). 복구한 뒤 다시 만들었다.

## 8. 호스트·사용자 이름은 신뢰하지 않는 입력이다(인젝션 시험에서 확인)

- `dashboard.incident_queue.host_name`, `dashboard.asset_names`, 근거 API의 `host.name`과 `zeekad_asset_observations`에 실리는 이름은 NTLM의 호스트·사용자 이름과 Kerberos의 클라이언트 이름이다. 접속하는 쪽이 마음대로 정하는 문자열이고, 파이프라인은 관측한 그대로 넘긴다(길이·글자 검사 없음).
- 공격 문장 16종(HTML·마크다운·Slack 표기, 제어·방향 전환 문자, 4,000자 문자열 포함)을 넣어 보면 그대로 실린다([tests/test_prompt_injection.py](../tests/test_prompt_injection.py)의 `PointDAssetNamesTest`).
- 대시보드에서 할 것: HTML 이스케이프, 링크나 마크다운으로 해석하지 않기, 길이 자르기, 제어 문자·방향 전환 문자를 지우거나 보이게 하기. 이름을 조건으로 쓰는 기능(검색, 예외 규칙)에서도 그대로 믿지 않는다.
- 이 이름은 LLM·판단 모델·Slack 알림에는 가지 않는다.
- LLM 보고서의 문장(`dashboard.incident_reports`)도 사람이 쓴 글이 아니다. 파이프라인이 제어 문자, URL 표기, IP 모양, 긴 문장, 스키마 밖 칸은 걸러 템플릿으로 바꾸지만, 문장의 뜻("정상이다" 같은 서술)은 판별하지 않는다. 화면에서 LLM이 쓴 글임을 표시하고 이스케이프한다.

## 10. 보고서 조회 인덱스(2026-11-27 추가, migration 019, Q87)

- 대시보드가 알린 느려짐(최신 큐 뷰가 사건 행마다 `agent_report`를 훑음)에 맞춰 zeek_AD에 같은 인덱스를 넣었다: `zeekad.agent_report_incident_job_idx` = `agent_report (incident_id, job_id DESC)`. 파일은 `db/migrations/019_agent_report_incident_index.sql`이다.
- 표·뷰·함수·권한과 조회 결과는 바뀌지 않는다. 데이터 계약의 `latest_incident_queue` 절에 한 줄 적었다.
- 공개용 사본에 넣는 스크립트는 **같은 이름에 `IF NOT EXISTS`**로 써 달라. 그러면 019가 적용된 VM에서 다음에 뜬 스냅샷에서는 그 스크립트가 아무 일도 하지 않는다. 지금 공개 스냅샷(2026-11-26)에는 019가 없다.
- 배포 VM에는 2026-11-27에 적용했다(최신 큐 조회 결과는 같고 약 150ms → 22ms). 이제 VM에서 뜨는 스냅샷에는 019가 들어 있어 사본 스크립트는 아무 일도 하지 않는다.
